# Контроль дорожной разметки

Учебный проект по курсу «Fullstack».

Приложение для дорожной службы, которая следит за состоянием разметки на улицах города.
Инспектор загружает фотографии участков, на снимках отмечаются дефекты разметки
(стёртые линии и пробелы), а по найденным дефектам диспетчер формирует задания на ремонт.

Текущий этап — лабораторная работа №2: серверная часть, база данных и API.
Интерфейс пока работает на демонстрационных данных, их подключение к API выполняется
в лабораторной работе №5.

## Пользовательские сценарии

1. Инспектор загружает фотографию участка улицы и указывает адрес и дату съёмки.
2. Загруженный снимок попадает в общий список, где видно его статус обработки.
3. Диспетчер открывает реестр дефектов, фильтрует его по типу и серьёзности.
4. По выбранному дефекту диспетчер создаёт задание на ремонт с исполнителем и сроком.
5. Диспетчер отслеживает статусы заданий на ремонт.

## Экраны

| Экран | Маршрут | Назначение |
| --- | --- | --- |
| Загрузки | `/uploads` | Список загруженных снимков: адрес, дата, статус обработки, число дефектов |
| Новая загрузка | `/uploads/new` | Форма добавления снимка участка |
| Дефекты | `/defects` | Реестр найденных дефектов с фильтрами по типу и серьёзности |
| Задания | `/tasks` | Задания на ремонт: исполнитель, срок, статус |

Корневой адрес `/` перенаправляет на `/uploads`. Несуществующие адреса открывают
страницу «Страница не найдена».

## Стек

Frontend:

- React + TypeScript, сборка через Vite
- Mantine — библиотека UI-компонентов
- React Router — клиентская маршрутизация

Backend:

- Python + FastAPI
- PostgreSQL + SQLAlchemy
- Pydantic — конфигурация и схемы валидации

## Структура проекта

```
frontend/             клиентская часть (React + TypeScript)
  public/photos/      демонстрационные снимки участков
  src/
    components/       общие компоненты интерфейса (макет, бейдж статуса)
    pages/            экраны приложения, по файлу на маршрут
    data/             демонстрационные данные и подписи статусов
    utils/            вспомогательные функции форматирования
    types.ts          типы предметной области
    theme.ts          настройки оформления Mantine
    App.tsx           описание маршрутов
    main.tsx          точка входа, подключение провайдеров
backend/              серверная часть (FastAPI)
  app/
    core/config.py    конфигурация приложения
    db/               подключение к БД, сессии, создание таблиц, демо-данные
    models/           модели SQLAlchemy (таблицы и связи)
    main.py           создание приложения и подключение маршрутов
  requirements.txt    зависимости Python
  .env.example        пример настроек окружения
```

Экраны отделены от общих компонентов, данные предметной области и их типы вынесены
из компонентов в отдельные модули. В лабораторной работе №3 структура frontend будет
приведена к упрощённому варианту Feature-Sliced Design.

## Модель данных

Три таблицы, связанные внешними ключами:

```
uploads 1 ──< N defects 1 ──1 repair_tasks
```

| Таблица | Поля | Связи и ограничения |
| --- | --- | --- |
| `uploads` | `id`, `street`, `section`, `captured_at`, `uploaded_by`, `photo_url`, `status`, `created_at` | `status` — перечисление `upload_status` |
| `defects` | `id`, `upload_id`, `type`, `severity`, `wear_percent`, `length_m` | `upload_id` → `uploads.id` (ON DELETE CASCADE), индекс; `wear_percent` в диапазоне 0–100, `length_m` больше нуля |
| `repair_tasks` | `id`, `defect_id`, `crew`, `due_date`, `status`, `comment`, `created_at` | `defect_id` → `defects.id` (ON DELETE CASCADE), уникальный — не более одного задания на дефект |

Перечисления (`upload_status`, `defect_type`, `defect_severity`, `task_status`) создаются
как собственные типы PostgreSQL, поэтому значение вне списка в таблицу не попадёт.

Адрес хранится только у снимка: дефект и задание получают его по цепочке связей.
Количество дефектов у снимка не хранится отдельно, а считается по связанным записям.

Интерфейс пока использует демонстрационные данные из `frontend/src/data/mockData.ts`;
подключение экранов к API выполняется в лабораторной работе №5.

## Запуск frontend

Нужен Node.js версии 20 или новее.

```bash
cd frontend
npm install
npm run dev
```

Приложение открывается на http://localhost:5173

Остальные команды:

```bash
npm run build     # production-сборка в папку dist
npm run preview   # посмотреть собранную версию
```

## Запуск backend

Нужны Python 3.11–3.13 (проверено на 3.13) и Docker для базы данных.

Настройки окружения:

```bash
cp backend/.env.example backend/.env
```

База данных:

```bash
docker compose up -d db
```

Поднимется PostgreSQL 16 на порту 5432 с параметрами из `backend/.env`.
Данные сохраняются в именованном томе `pgdata` и переживают перезапуск контейнера.

Сервер приложения:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Создание таблиц и демонстрационные данные:

```bash
python -m app.db.init_db     # создаёт таблицы и типы-перечисления
python -m app.db.seed        # заполняет базу демо-данными, повторный запуск безопасен
```

Запуск сервера:

```bash
uvicorn app.main:app --reload
```

API доступно на http://localhost:8000, интерактивная документация — на
http://localhost:8000/docs

Команды сервера запускаются из каталога `backend`: оттуда читается файл `.env`.
